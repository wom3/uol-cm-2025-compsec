Incident Response Memo: OpenData Analytics Breach
Overview:
A recent breach occured due to unauthorized SSH accessing default credentials Linux-based virtual machines. The absence of a firewall privilege restrictions allowed the attacker to escalate access and exfiltrate sensitive data.
Configuration Weaknesses
Default login credentials: Using unmodified default usernames and passwords made brute-force or credential stuffing trivial.
Disabled firewall: Without packet filtering, inbound SSH connections were unrestricted.
Lack of privilege separation: All the users had escalated privileges, violating the principle of least privilege.
Unpatched system components: Likely outdated SSH or kernel versions increased exploitability.
Missing audit and intrusion detection: No logs or alerts to flag suspicious login attempts.

Recommended Linux Security Practices
Enhance strong authentication: Disable password-based SSH; use key-based authentication with passphrases.
Activate and configure firewalls: Employ ufw or firewall to restrict inbound traffic to essential ports.
Implement least privilege: Use sudo with granular permissions and separate administrative accounts.
Regular patching: Automate updates via cron or configuration management tools like Ansible.
Disable unused services: Reduce attack surface by stopping unnecessary daemons
Enable SELinux or AppArmor: Apply mandatory access controls to confine processes.

Feedback
Incident overview 
The security incident at OpenData Analytics resulted from basic OS-level misconfigurations. A publicly accessible Linux server was compromised through default SSH credentials, allowing unauthorised access to client data and internal project files. 
1. Configuration weaknesses
The following configuration weaknesses likely contributed to this breach.
	•	The server was running with default login credentials, which allowed the attacker to log in via SSH.
	•	The firewall had not been activated, leaving the system open to external access.
	•	There were no enforced privilege restrictions, so once access was gained, the attacker could view sensitive project files and client credentials.
These are examples of the kinds of issues that a Linux hardening audit tool (such as hardening.sh from the Harbian project) has been designed to flag, since it checks for insecure defaults, firewall status and privilege-related risks.
2. Linux-based security practices to prevent future incidents
To prevent similar breaches, the organisation should apply Linux hardening practices as discussed in the lecture:
	•	Remove insecure defaults such as default usernames and passwords.
	•	Enable and configure the firewall so that it only exposes required services.
	•	Restrict user privileges, ensuring that accounts only have the rights necessary for their role.
	•	Run regular audits with tools like hardening.sh to test system configuration against a broad set of best practice checks (e.g. permissions, SUID files, account setup).
3. Tools and techniques for monitoring and maintenance
For ongoing maintenance of a secure Linux environment, the organisation should:
	•	use auditing scripts like hardening.sh to identify weaknesses and misconfigurations
	•	review the audit output regularly and take corrective action where failures are identified
	•	keep systems up to date with patches, as the hardening tools themselves are updated frequently to reflect newly discovered vulnerabilities.
